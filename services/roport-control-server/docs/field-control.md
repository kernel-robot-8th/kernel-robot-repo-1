# 요청 기반 통합 관제

## 실행 경계

브라우저 → FastAPI → 기존 Unix socket → **FleetControl 실행부 1개** → MQTT → Pinky/OMX.
실행부가 역할·작업·선반·예약·결과를 한 운영 PostgreSQL 상태에 저장한다. UI는 실행부의 같은 상태를 읽으며 별도 재고를 만들지 않는다. API가 DB를 폴링하는 구조는 아니다. 외부 서비스 예약/수령은 인증된 WSS → inbox/outbox → 같은 실행부로 연결한다. 서비스 DB와 관제 DB의 소유권은 분리한다([서비스 연결](service-link.md)).

`executor/fleet.py`는 배정/진행 규칙, `fleet_runtime.py`는 MQTT/WSS 연결, `fleet_socket.py`는 조작 접수다. API와 웹은 MQTT를 직접 발행하지 않는다. 시작만으로 움직이지 않으며 UI의 실행 승인 후 준비된 요청을 처리한다.

## 현재 결정과 동작

| 항목 | 구현 |
| --- | --- |
| Pinky | 고정 3자리. 기본 pinky1/2 물류, pinky3 스마트카트. 정지·유휴 시 역할 변경/배정 제외. 최초 미배치 슬롯은 시작 전에 제외. 제외한 기체의 마지막 점유를 빈자리로 지우지 않음 |
| 물류 대기 | N16/N17 중 비점유·비예약 자리. 번호별 고정 복귀 없음 |
| 스마트카트 대기 | H1/H2 중 비점유·비예약 자리 |
| 창고 | N01, OMX3. 상차 결과의 `package_size`로 small/large 분류; unknown은 N01에서 판단 대기 |
| 선반 a열 | 1a/2a, N21, 작은 물품, OMX1 단독 |
| 선반 b열 | 1b/2b, N11, 큰 물품, OMX1+2 공동 |
| 선반 c열 | 1c/2c, N22, 작은 물품, OMX2 단독 |
| N12 | line→Nav2와 Nav2→line 모두 지원. 복귀는 보정 목표 pose·정지·중앙 IR 안정 확인 뒤 다음 라인 경로 승인 |

입고: 유휴 물류 기체 → N01 상차 → 크기에 맞는 빈 칸·팔·접근 경로 선택 → 선반 안착/물품 해제/팔 복귀 확인 → 빈 물류 대기 자리.

입고를 마친 빈 물류 기체의 복귀는 통행을 막지 않는 중간 노드 단위로 진행한다. 새 입고 요청이 있으면 해당 구간 완료와 최신 정지·라인 제어 해제를 확인한 뒤, 현재 위치에서 새 작업에 배정할 수 있다. 이전 작업에는 `return_reassigned_to`를 기록하고 새 작업과 복귀 자리 예약을 함께 저장한다. 이동 중 명령을 덮어쓰거나 STOP/HOLD로 끊지 않으며, 새 요청이 없으면 원래 대기 자리까지 복귀한다. OMX 구역 출발 전·상하차 중·스마트카트 작업은 이 재배정 대상이 아니다.

출고: 실제 재고 칸 확인 → 유휴 스마트카트 → 해당 칸 상차 → N12 → Nav2 고객 목표 → **고객 수령 근거 대기** → 보정 N12 복귀 목표 → line 전환 → 빈 카트 대기 자리.

물품 하나에 활성 작업 하나를 두며 같은 요청 ID/내용은 같은 작업을 반환한다. 실제 도착 command, 포장품, 선반 칸, 팔 boot와 정지·복귀·해제 근거가 맞아야 재고/다음 단계가 바뀐다. 고객 수령은 로봇 작업 완료로 대신하지 않는다. 선반에 안착이 확인되지 않은 물품의 출고 요청은 접수 단계에서 거절하며, 작업·재고·명령을 변경하지 않는다. 서비스의 여러 물품 요청도 전체 목록을 먼저 검사하여 일부 물품만 작업으로 남기지 않는다.

## 통행과 실패

**서로 겹치지 않는 구간은 여러 Pinky가 동시에 주행**한다. 기체·복귀 자리·선반 칸·노드·양방향 간선을 예약하며, 이동 진행이 확인되면 지난 구간을 해제한다. 노드 감지는 앞쪽 IR 기준이므로 들어온 간선은 다음 노드 확인까지 유지한다. 지난 노드는 현재 위치부터 목표까지 남은 경로와의 최소 간격이 관제 설정의 `node_clearance_m` 이상일 때 해제한다. 짧은 구간을 여러 번 지났거나 이후 경로가 다시 가까워지는 경우에도 필요한 노드 보호가 유지되며, 진행 중 해제한 노드를 재예약하지 않는다. 아직 감지 중인 현재 교차점은 즉시 빈자리로 취급하지 않는다.

조기 노드 해제에는 `node_positions`(노드별 map 좌표 `[x, y]`, m)와 `node_clearance_m`(두 기체의 회전·적재 외곽, IR 위치, 감지 오차를 포함한 최소 간격)이 필요하다. 가상 실행기는 최신 실측 좌표와 0.35m를 생성한다. 이는 기본 기체의 두 회전 외곽 `2 × hypot(0.06 + 0.03, 0.06 + 0.03)`에 IR 0.03m·감지 여유 0.05m·테이프 반폭 0.012m를 더한 약 0.347m를 올린 값이다. N07–N23(0.487m)은 N23 감지 때 N07 노드만 해제하고 N07–N23 간선은 계속 보호한다. 짧은 N15–N05(0.198m)는 기존 보호를 유지한다. 기존 설정에 `node_clearance_m`가 없으면 이전 노드도 다음 노드까지 보호한다. 실물에 적용하려면 적재물까지 포함한 외곽으로 간격을 검증해 해당 설정을 추가해야 하며, 가상값을 현장 안전 확인값으로 간주하지 않는다. MQTT 필드는 변경하지 않는다.

이 거리 보호는 활성 주행 명령의 노드 예약에 적용된다. 명령 완료 후에는 기존 현재 노드 점유·주차 배정 규칙을 사용하며, 모든 정지 기체·임의 교차 구간 사이의 차체 간격까지 보장하는 물리 충돌 판정은 아니다. 거리 비교는 좌표 소수점 계산 오차만 1e-9m까지 같은 값으로 처리한다. 간선 키는 노드명의 `%`·`-`를 이스케이프하며 현재 지도에서 사용하는 `edge:N07-N23` 같은 키는 유지한다.

경로가 겹치면 먼저 확보할 수 있는 구간까지만 명령을 보내고 중간 노드에서 정차한다. 다른 기체의 현재 목적지로 가는 길이나 상하차 구역 출구를 막는 대기점은 피한다. 예약이 해제되면 경로를 다시 계산하여 자동으로 이어간다. 완료 이벤트 뒤 최신 위치·방향·정지 상태를 받은 다음 명령을 보내며, 중간 도착은 최종 목적지 도착과 구분하므로 OMX 작업이나 다음 업무 단계를 시작하지 않는다. OMX host는 한 번에 한 작업을 실행하며, 다른 구역의 Pinky 주행과는 병행할 수 있다. 시간 최적 경로·우선순위 선점은 구현하지 않았다.

활성 라인 주행의 일시 점유·예약은 경로 탐색에서 영구 장애로 취급하지 않는다. 짧은 경로의 안전한 구간까지만 이동하고, 막힌 구간이 실제 해제되면 이어간다. 예를 들어 N05의 후행 기체는 선행 기체의 N07 후방 보호가 해제되기를 기다린 뒤 `N05 → N07 → N18 → N01`로 이동한다. N07을 피해 N15로 되돌아가는 우회는 선택하지 않는다. 주행 명령이 없는 정지 기체는 계속 장애로 취급해 우회할 수 있다. 거리·불필요 회전을 줄이는 정책이며 모든 상황의 최소 완료 시간을 보장하지 않는다.

등록 기체의 라인 위치가 불명이면 새 경로를 배정하지 않는다. 역할 제외 기체도 마지막으로 확인된 점유를 유지하며, 정상 Nav2의 공용 공간 상태는 라인 위치 불명과 구분한다. 주행 중에는 직전 보호 구간과 남은 경로를 다시 검사해 새 점유·위치 불명에 HOLD와 모든 활성 명령의 정지를 요청한다. 해제가 확인된 구간이나 경로 밖의 알려진 점유는 주행을 막지 않는다.

명령을 먼저 저장한 뒤 발행하며 결과를 저장한 뒤 event_stored를 보낸다. ACK·시간 초과만으로 작업/점유를 완료 처리하지 않는다. 통신 단절·응답 지연·참여 기체 재시작·실행부 재시작 중 미완료 명령·팔 실패는 HOLD와 정지 요청으로 이어진다. 늦게 도착한 완료는 기록하되 HOLD를 자동 해제하지 않는다. 실행부 재기동은 항상 승인 대기로 시작하며 지도/그래프가 바뀌면 기존 작업을 자동 재사용하지 않는다.

OMX는 정차뿐 아니라 Pinky의 라인 주행 비활성·제어권 해제·미완료 명령 없음을 작업 전과 작업 중에 확인한다. Pinky MQTT 연결 오류는 송수신 프로세스를 종료시키지 않고 정지 상태를 유지하며, 재연결 뒤 상태를 보고하되 자동 재주행하지 않는다.

HOLD 후 실제 기체/물품 위치를 조정하는 운영 복구 UI는 후속이다. 확인 없이 파일/DB를 지워 재개하는 절차는 제공하지 않는다. 가상 시험은 새 실행 폴더로 독립 재현한다.

## 가상 실행

관제 패키지 디렉터리에서 실행한다. 기존 지도 설정은 `run_virtual_trial.py`의 MAP/LAYOUT 선택을 재사용한다. Mosquitto가 PATH에 없으면 `MOSQUITTO_BIN`에 실행 파일을 지정한다.

```bash
bash tools/start_virtual_ui.sh
```

스크립트는 저장된 현재 checkout과 잠금 파일 기준으로 실행한다. Python 환경과 웹 자산을 확인하고, 관제·가상 장비가 준비되면 마지막 줄에 조작 키를 표시한다. GitHub pull은 하지 않는다. 코드 수정 후 기존 터미널에서 **Ctrl+C → 같은 명령 재실행 → 웹 새로고침**하면 새 코드·새 키가 적용된다. 각 실행의 이전 기록은 보존한다. 8000 포트가 사용 중이면 기존 실행을 종료하거나 `bash tools/start_virtual_ui.sh --port 8001`을 사용한다. 이 PC에서는 기존 Mosquitto 캐시도 자동으로 찾는다.

원본 화면 `http://127.0.0.1:8000/ui/?mode=fleet`에서 마지막 줄의 키를 입력한다(`ui-key.txt`에도 저장). **역할 → 입고 요청 → 관제 실행** 순서다. `package-small-1`은 small, `package-large-1`은 large로 모의 OMX3가 보고한다. 입고 완료 후 같은 물품으로 출고 요청, 목적지 선택, 고객 도착 후 가상 수령 확인을 실행한다. 키는 브라우저 메모리에만 보관하고 터미널 출력·키 파일은 공유하지 않는다.

```bash
# 새 폴더에 소형 입고→출고→고객 수령→N12 복귀를 자동 검증한다.
uv run python tools/run_virtual_fleet.py --verify --timeout 1200
```

Ctrl+C로 해당 실행에서 생성한 프로세스를 종료하며 결과/로그/config는 `~/roport-trial/fleet/실행시각/`에 남는다. `--output`은 존재하지 않는 새 폴더를 지정한다. 브로커는 loopback이고 실제 로봇에는 접속하지 않는다. 가상 기본 속도는 0.08m/s다. 실제 Pinky TrialDriver/TrialLogic/RouteExecutor를 사용하고 센서/바퀴/Nav2/OMX 장치 I/O는 모사한다. 자동시험에서 센서 시간을 가속한 결과와 이 실행기의 1배속 결과를 구분한다.

기존 `run_virtual_trial.py`의 1대/2대/스마트카트 구간 시험은 유지한다. 내부 trial DTO는 호환용으로 남고 Pinky 전송은 새 field 규약으로 변환한다. 기존 OMX cooperative 시험 경로는 이전 trial 계약이며 새 fleet 경로의 OMX 송수신과 혼동하지 않는다.

## 실물에 옮길 때

같은 fleet 실행부와 MQTT 규약을 쓰고 Pinky의 장치 driver 및 OMX의 장치/정책/비전 factory를 실물로 교체한다. `fleet.json`에는 현장 지도/그래프, 0.06m/s 기본 속도, 보정한 고객 목표/N12 복귀 pose, 실제 OMX model/calibration을 입력한다. 가상 `sim-model/sim-cal`을 실물 값으로 사용하지 않는다. OMX policy·팔 복귀·정지·안착 센서 adapter는 실제 설치값이 필요하다([OMX README](../../roport-omx/README.md)).

동시 주행을 실물에 적용하려면 Pinky의 `roport_line_nav/{graph,executor,line_nav_node}.py`와 `roport_pinky/trial_driver.py`를 함께 업데이트해야 한다. 기존 MQTT `line_route_command`의 중간 노드 목표를 사용하며 전송 스키마는 바뀌지 않는다. ROS 내부 `hold_at_goal`로 교차점 중심에서 정차·재출발한다. 교차점 정차 오차·차체 여유·제동 거리는 현장에서 검증해야 한다. 실물 기본 속도는 이번 가상 속도 변경과 별도로 0.06m/s를 유지한다.

운영 DB를 명시적으로 설치하고 `ROPORT_DATABASE_URL`, broker 환경변수, API의 `ROPORT_FLEET_SOCKET`·`ROPORT_TRIAL_TOKEN`·지도 경로를 설정한다. `fleet.json`을 hardware/field_verified로 바꾸는 것은 현장 확인 후다.

```bash
uv run python -m roport_control_server.adapters.db.service_tasks
uv run python -m roport_control_server.executor.fleet_runtime \
  --config /absolute/path/fleet.json --socket /absolute/path/fleet.sock \
  --hardware-authorized
# 다른 터미널: 동일 socket, 지도, 조작 키 환경변수 설정
uv run uvicorn roport_control_server.adapters.api.app:app --host 127.0.0.1 --port 8000
```

하드웨어 실행은 파일 journal을 받지 않는다. 원격 실물 조작은 HTTPS, 현장 로컬 조작은 loopback이다. 기존 조작 키는 서비스 사용자 권한 체계를 대신하지 않는다. 운영 공개 배포·장시간 운영·실물 캘리브레이션 검증은 별도다.

## 남은 결정

- 크기 정보의 최종 발행 주체와 unknown 물품 운영 처리.
- 예약시각을 만족하는 준비/출발 정책. 현재 유효 요청을 즉시 대기열에 넣고 가능한 순서로 처리한다.
- 예약 이후 포장 명세 확정/변경 및 고객 인증·분할 수령 서비스 API.
- 개별/공동 팔 작업의 실제 장치 factory·정책·센서 보정, N12 역전환 현장 오차.
- HOLD 후 위치/재고 확인과 재개 절차, 동시 주행의 현장 물리 간섭·제동거리·장시간 교착 검증.

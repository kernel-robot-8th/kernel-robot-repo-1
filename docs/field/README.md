# Fleet 현장 배포 준비와 복구

저장소의 `services/roport-control-server`에서 실행한다. 다음 명령은 새 디렉터리에 배포 자료를 만들고 설정 오류를 JSON으로 기록한다.

```bash
uv run python tools/prepare_field.py --output /tmp/field-handoff
(cd /tmp/field-handoff && sha256sum -c SHA256SUMS)
uv run python tools/check_field.py --bundle /tmp/field-handoff --targets pinky1 omx3 --output /tmp/field-check.json
```

- 원본 묶음을 보관하고 작업 사본을 사용한다. Pinky에는 해당 슬롯의 `trial.json`, `pinky_mqtt/`, 지도와 필요한 ROS 패키지를 전달한다. OMX에는 `omx/`를 전달한다. 기존 보정·환경·journal은 기체에 유지한다.
- 새 설정은 현장 확인 전 상태다. 실제 지도와 복귀 목표 `n12_goal`, 기체 배정, 모델·보정 버전을 확인한 뒤 작업 사본의 관제 및 대상 Pinky 설정에 현장 확인을 기록한다. 초기 점검은 미확정 항목을 표시하고 종료 코드 1을 반환한다.
- 이미 실행 중인 기체 상태를 관찰할 때는 브로커 환경을 지정하고 점검 명령에 `--listen --seconds 5`를 추가한다. 기본 스마트카트 슬롯을 점검하는 예인 `--targets pinky3 --nav2 pinky3`은 해당 기체의 Nav2 및 위치 추정 준비도 확인한다. 이 도구는 동작 명령을 발행하지 않는다.
- 점검 실패 시 보고서의 대상·원인을 확인한다. 이전 배포로 돌아갈 때는 보관한 원본과 해당 시점의 지도·코드 해시를 대조하고 미완료 명령의 journal을 보존한다. 재시작 후 HOLD 해제 및 재출발은 운영자가 별도로 결정한다.

점검은 N12 복귀 목표의 ID가 `N12_RETURN`인지 확인하고, 배포된 지도·레이아웃에서 계산한 복귀 기준 자세와 비교한다. 기준 자세는 N12에서 센서 오프셋 3 cm를 적용한 차체 중심과 라인 진입 방향이다. 위치 편차 및 목표 허용오차 상한은 3 cm, 각도는 0.08 rad이다. 현장 실측과 정렬 확인은 별도로 수행한다. 상태 구독 시 각 Pinky의 개별 역할 경로 시작 노드를 대조하며, 같은 기동에서 순번이 증가한 최근 두 표본 모두 관제 시계 기준 과거 3초~미래 1초 이내여야 한다.

### 점검 결과 해석

- 상태 구독 전 관제 PC와 로봇 시계를 맞추고 현장 작업 사본에 **실제 기체 / MQTT 슬롯 / 배정 역할 / 대기 노드**를 기록한다. 시작 위치 일치는 관측 결과이며 배차 가능 여부는 Fleet이 역할별 대기점과 점유 상태로 별도 판단한다.
- `scope=settings_only`는 파일·설정 검사다. MQTT 구독을 마친 경우에만 `mqtt_checked=true`이며, 각 대상의 준비 여부는 `mqtt.targets`에 표시한다.
- `bundle.source_dirty`는 생성 당시 Git 작업 트리의 수정 여부다. 작업 사본에서 바꾼 프로필은 `modified_profiles`, 해시가 달라진 실행 파일·지도 등은 `damaged_files`에 표시한다. 원본 파일 누락·손상은 점검 실패다.
- N12의 공칭 자세는 지도상 N08→N12 방향과 반대 방향을 보는 차체 기준이다. 3 cm·0.08 rad는 **공칭 대비 허용 편차**다. Nav2가 도착을 보고하더라도 라인 전환에 필요한 실제 정렬과 센서 상태는 현장에서 확인한다.

### 인도장 일반 HOLD 해제

팔·물품·Pinky 상태 확인 후 관제 실행부 계정에서 `uv run python tools/release_workcell.py --socket "$FLEET_SOCKET" --hold-command-id "$HELD_COMMAND" --arms-confirmed --box-confirmed --pinky-confirmed`를 실행한다. 현재 Host 기동과 보류 명령이 일치하고 양팔 정지·홈·빈 그리퍼가 확인되면 해제 결과가 기록된다. 소켓이 확인한 요청 프로세스의 UID와 요청 ID를 기록한다. 비상 정지·강제 종료, 재시작으로 기존 실행 결과를 알 수 없는 경우, 정지 여부나 취소 사유가 확인되지 않은 경우에는 Host에서 현장 확인 후 해제한다. 관제 HOLD 해제와 운행 재개에는 별도 조작이 필요하다.

현장 작업 사본에 기체 배정을 기록한다. 역할 변경 시 같은 표와 대상 프로필을 함께 갱신한다.

### 상차 전 라인 유실 복구

- 관제가 `line_lost`가 난 입고 주행과 점유 구간을 HOLD로 보존한다.
- 현장에서 정지한 Pinky를 N16의 정차선에 놓고 N14를 향하도록 맞춘 뒤 통로가 비어 있는지 확인한다.
- 실물 실행부는 라인 유실 후 잠긴다. 정차·재배치 확인 후 기존 실행부를 종료하고 같은 기체·journal로 `ROPORT_PINKY_START_NODE=N16`을 지정해 다시 띄운다. 보고된 노드와 방향은 시작 설정을 확인하는 값이다. 실제 차체 위치와 방향은 현장 운영자가 확인한다.
- **라인 유실 · N16 재배치 후 기존 입고 재준비**를 선택한다. 관제는 실패 이후 같은 지도·그래프의 최신 상태, 현재 기동, 유휴·정지 상태와 시작 방향, N16 점유 여부를 확인한다.
- 확인 후 **보류 해제**, **요청 처리 시작**을 각각 누른다. 양쪽 확인만으로 출발하지 않는다.
- 가상 재현은 `tools/run_virtual_fleet.py --d660-line-loss`를 사용한다. 주행과 재배치는 가상 Pinky에서만 재현한다.

### 스마트카트 카드 추종

- 현장 카드 번호를 먼저 정하고 인식 노트북의 `roport_follow --follow-card`와 패드에서 고르는 번호를 일치시킨다. 인식기는 실행당 카드 한 장만 추적한다. 관제는 패드의 선택을 Pinky로 전달한다.
- 검증 대상으로 배정된 Pinky에 관제와 같은 현장 번들의 `pinky_mqtt/`를 배포한다. 추종 명령을 해석하는 `field_pinky.py`와 `field_wire.py`가 포함되어야 한다.
- 추종 승인 전 현장에서 카드가 카메라에 보이는 자세인지 확인한다. 이 경로는 Pinky 드라이버 기본값인 카드 유실 1초와 목표 거리 0.5 m를 사용한다. 카드 유실·인식 실패·시간 종료 시 해당 카트의 추종만 멈춘다. 운영자는 새 정지 상태 확인 후 재개하거나 복귀시킨다.
